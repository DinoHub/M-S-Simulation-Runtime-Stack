# Autonomy Developer Test Plan

**Product:** M&S Simulation Runtime Stack (dashboard → scenario authoring → generated simulation stacks)
**Audience:** an autonomy developer integrating their own planner / autonomy stack against the product
**How to use:** work top to bottom. Each test is a checkbox, the exact commands to run, and what to expect. Check the box only when the expectation held. Each phase states an objective and an **exit gate** — don't start the next phase until the gate holds. Copy this file per campaign (`test-runs/<date>-<autonomy-build>.md`) so checked boxes become the campaign record.

Assumes a ROS 2 (Humble) autonomy workload against AirSim/Unreal + ArduPilot or PX4 SITL stacks generated by this product.

### Session setup

Set these once per shell — all commands below use them. Adjust the prefix to your launched scenario (see `docker ps` after launch):

```bash
export STACK=ardupilot-blocks-blocks-authoring-single   # container name prefix
export ARDUPILOT=$STACK-ardupilot-drone-0
export BRIDGE=$STACK-airsim-bridge-c1
export QGC=$STACK-qgroundcontrol-x11
export SIM=$STACK-unreal-airsim
# helper: run a ROS 2 command inside the bridge container
r2() { docker exec "$BRIDGE" bash -lc "source /opt/ros/humble/setup.bash 2>/dev/null; source /install/setup.bash 2>/dev/null; ros2 $*"; }
```

## Phase 0 — Environment preflight

**Objective:** prove the product itself is healthy on this machine before any autonomy code enters the picture, so later failures implicate the autonomy integration, not the install.
**Exit gate:** all boxes checked; preflight endpoint fully green.

- [ ] **P0-1 Dashboard up**
  ```bash
  make dashboard
  curl -s localhost:8001/api/scenario/preflight | python3 -m json.tool
  ```
  Expect: http://localhost:3001 loads in a browser; JSON has `"ready": true`. Note: backend can take ~2 min on first boot if the telemetry DB is absent (it retries postgres before starting).

- [ ] **P0-2 Preflight checks green**
  Inspect the JSON from P0-1. Expect: `docker_daemon`, `authoring_image`, `generator_image`, `exports_writable`, `display` all `"ok"`; `xauthority` at worst `"warn"` after running:
  ```bash
  DISPLAY=:0 xhost +si:localuser:$USER
  ```

- [ ] **P0-3 Registry access**
  ```bash
  docker pull dhdevspace/auto_mns:tevv-web-dashboard-frontend-latest
  docker inspect airsim-dashboard-api --format '{{range .Mounts}}{{.Destination}}{{"\n"}}{{end}}' | grep docker/config
  ```
  Expect: pull succeeds (host Hub login valid); second command prints `/root/.docker/config.json` — the backend has creds and can pull on your behalf. If it prints nothing, dashboard-launched stacks will fail on any missing image (see gotchas below).

- [ ] **P0-4 X11 for GUI containers**
  ```bash
  docker logs $QGC 2>&1 | grep -i 'display\|cannot open'
  echo $XAUTHORITY
  ```
  Expect: no `cannot open display`. GDM hosts: `XAUTHORITY=/run/user/<uid>/gdm/Xauthority`, not `~/.Xauthority`.

- [ ] **P0-5 Env layering understood** — read Appendix A; state which of the four env layers wins for your launch path.

> **Gotchas:** generated stacks default `MNS_IMAGE_PULL_POLICY=always` — without backend creds, launches hard-fail even when all images are local (fix: creds mount, or `sed -i 's/=always/=missing/' generated/<scenario>/.env`, which reverts on regeneration). `compose/<scenario>/.env` silently shadows the top-level `.env`. A stale `SCENARIO=` in `.env` breaks `make stop` auto-detect — stop with the explicit scenario argument.

## Phase 1 — Product smoke, no autonomy

**Objective:** a stock scenario runs end-to-end under manual control only, proving sim, SITL, GCS, and lifecycle plumbing.
**Exit gate:** manual takeoff + land completed; stop leaves zero orphans.

- [ ] **P1-1 Generate + launch stock scenario**
  Dashboard → generate and launch `blocks` (single drone), then:
  ```bash
  watch -n 5 'docker ps --format "{{.Names}}\t{{.Status}}" | grep "$STACK"'
  ```
  Expect: all stack containers `Up`/`healthy` within 2 min; no restart loops.

- [ ] **P1-2 Sim ↔ SITL FDM link**
  ```bash
  docker logs $ARDUPILOT 2>&1 | grep -i -E 'connect|airsim|fps' | tail -20
  ```
  Expect: AirSim connection established; frame rate reported (SITL heartbeat healthy).

- [ ] **P1-3 GCS link**
  Open the QGC window. Expect: vehicle visible with live telemetry. If not:
  ```bash
  docker exec $ARDUPILOT ss -unp | grep 14550
  docker exec $ARDUPILOT getent hosts qgroundcontrol-x11
  ```
  The socket's peer must be the QGC container's IP. A peer of `255.255.255.255` means SITL was given a hostname — its `udpclient` does **not** resolve names and silently falls back to broadcast. Fix the target to an IP (or resolve in the launch script) and restart the SITL container.

- [ ] **P1-4 Manual mission**
  ```bash
  cd ~/MnS-Integration-Platform
  tools/pilot_control.sh $ARDUPILOT --profile ardupilot --backend mavlink \
    --mavlink-runner container --mavlink-url tcp:127.0.0.1:5762 --dry-run
  # then the same command without --dry-run
  ```
  Expect: dry-run prints the resolved contract; live run switches mode → GUIDED, arms, takes off, lands — no operator intervention in QGC. (SITL's TCP MAVLink is 5762/5763 inside the container; 5760 is not bound and no host ports are published.)

- [ ] **P1-5 Clean stop**
  Stop from the dashboard, then:
  ```bash
  docker ps --format '{{.Names}}' | grep "$STACK" || echo CLEAN
  ```
  Expect: `CLEAN`; relaunch from the dashboard works.

## Phase 2 — Sensor and interface contract

**Objective:** everything the autonomy stack will consume is present, correctly framed, and at rate — the input side of the contract.
**Exit gate:** every sensor in the scenario profile validated; bridge survives a sim restart.

- [ ] **P2-1 Topic inventory**
  ```bash
  r2 topic list
  r2 topic info <each sensor topic> -v | grep -c Publisher
  ```
  Expect: every sensor in the scenario's `SensorProfiles.yaml` has a topic with ≥1 publisher.

- [ ] **P2-2 Rates**
  ```bash
  r2 topic hz /<drone>/lidar --window 100     # repeat for camera, imu, odom
  ```
  Expect: within ±20% of the profile's configured rate, sustained 60 s.

- [ ] **P2-3 LiDAR geometry**
  Open Lichtblick (http://localhost:8082), subscribe to the lidar topic.
  Expect: point cloud upright and dense — no mirrored Z, no partial-sweep flicker (Cosys GPU LiDAR returns rotating partial sweeps and 5 floats/point; the bridge must handle both).

- [ ] **P2-4 TF tree**
  ```bash
  r2 run tf2_tools view_frames    # writes frames.pdf in the container
  ```
  Expect: connected `map → odom → base_link → sensor`; no orphan frames; correct per-drone prefixes.

- [ ] **P2-5 Sim time**
  ```bash
  r2 topic echo /clock --once
  r2 topic hz /clock --window 200
  ```
  Expect: monotonic, steady rate under load; autonomy nodes run with `use_sim_time:=true` and don't stall on clock jumps.

- [ ] **P2-6 Bridge restart resilience**
  ```bash
  docker restart $SIM
  sleep 30
  r2 topic hz /<drone>/odom --window 50
  ```
  Expect: topics resume without manually restarting the bridge. A bridge that raced the sim's RPC port shows 0 publishers forever — it must depend on sim *health*, not just start.

## Phase 3 — Autonomy in the loop

**Objective:** the developer's planner closes the loop — perception in, goals in, motion out — inside the generated stack.
**Exit gate:** goal missions complete with avoidance; planner survives restart mid-mission.

- [ ] **P3-1 Planner joins stack**
  Add your planner service to `generated/<scenario>/docker-compose.yml` (same networks, same `ROS_DOMAIN_ID`), relaunch, then from the planner container:
  ```bash
  ros2 topic list
  ```
  Expect: sensor topics visible; no DDS discovery gaps.

- [ ] **P3-2 Frame contract**
  Visualize your planner's local obstacle representation (Lichtblick/RViz) against sim ground truth.
  Expect: obstacles where the scenery is. Planners that need `LOCAL_OBS_TARGET_FRAME=map` must be configured so — a wrong frame yields plans through walls.

- [ ] **P3-3 Single goal**
  ```bash
  r2 topic pub --once /<goal_topic> <GoalMsgType> '<goal 20 m ahead, clear line>'
  ```
  Expect: vehicle plans, moves, arrives within tolerance; no collision.

- [ ] **P3-4 Obstacle avoidance**
  Same as P3-3 but the straight line to the goal intersects scenery.
  Expect: path deviates around the obstacle; clearance ≥ configured margin.

- [ ] **P3-5 Goal altitude behavior**
  Send goals at different Z values.
  Expect: vehicle honors or ignores goal Z per your `force_goal_z` configuration — behavior matches intent.

- [ ] **P3-6 Exploration lifecycle** *(if applicable)*
  Start your exploration planner; watch its status topic.
  Expect: started → exploring → done lifecycle observable on a topic that can drive `/run_state`.

- [ ] **P3-7 Autonomy restart**
  ```bash
  docker restart <planner-container>
  ```
  mid-mission, then send a new goal. Expect: planner rejoins, re-localizes, accepts the goal; rest of the stack unaffected.

> **Gotchas:** prebuilt planner images may bake workspace paths that need a hand-set `AMENT_PREFIX_PATH` when overlaid on the bridge image. ROS param YAML for namespaced multi-drone nodes needs wildcard headers (`/**/node_name:`) or params silently don't apply.

## Phase 4 — Metrics and evaluation

**Objective:** runs produce the artifacts used to score autonomy builds, under every trigger mode the campaign will rely on.
**Exit gate:** at least one fully evaluated run (metrics + evaluation + bag) exists and matches the dashboard.

- [ ] **P4-1 Goal-triggered run**
  Fly a goal mission with the metrics-collector default trigger, then check the run directory.
  Expect: `metrics.json` **and** `evaluated.json` produced; path-length metrics coupled to the goal.

- [ ] **P4-2 Manual trigger**
  ```bash
  r2 topic pub --once /metrics/start std_msgs/msg/Bool '{data: true}'
  # ... fly ...
  r2 topic pub --once /metrics/stop std_msgs/msg/Bool '{data: true}'
  ```
  Expect: `metrics.json` written on stop. **Known limitation:** external stop produces no `evaluated.json`/ES upload — plan scoring accordingly.

- [ ] **P4-3 run_state trigger** *(if enabled)*
  Drive `/run_state` from your planner lifecycle. Expect: collector starts/stops with transitions. Verify first that the collector's entrypoint actually enables `use_run_state_trigger` — it may be hardcoded off.

- [ ] **P4-4 Bag recording**
  Select record topics in the dashboard **before** launch ("0 record topics" records nothing), run, then:
  ```bash
  ls -lh ${TEVV_RUNS_DIR:-~/tevv-runs}/<run>/
  ```
  Expect: bag present and contains the selected topics.

- [ ] **P4-5 Sim-real eval** *(if enabled in the scenario)*
  Complete a run; expect the eval worker to write verdicts into the runs dir and the dashboard to display them.

- [ ] **P4-6 Dashboards**
  Open Grafana / the metrics UI. Expect: the run appears; plotted values match `metrics.json`.

## Phase 5 — Comms-under-test

**Objective:** validate the communication boundary the product exists to test — experiments degrade only the link under test, and the boundary carries only what it should.
**Exit gate:** boundary purity proven; behavior under degradation and partition characterized.

- [ ] **P5-1 Boundary purity**
  ```bash
  # find the agent_external bridge interface, then sniff it
  docker network inspect <stack>_agent_external -f '{{.Id}}' | cut -c1-12   # -> br-<id>
  sudo tcpdump -i br-<id> -A -c 200 2>/dev/null | grep -o '/shared[^ ]*\|/tf\|/clock\|sensor_msgs' | sort | uniq -c
  ```
  Expect: **only** `/shared/...` keys cross. Sensors, control, clock, TF, MAVROS, sim traffic must not appear — any leak invalidates comms experiments.

- [ ] **P5-2 Namespace ownership**
  Subscribe to `/shared/**` and attribute writers.
  Expect: `/shared/drone_N/...` written only by drone N; `/shared/swarm/...` drone-write/sim-read; `/shared/sim/...` sim-owned.

- [ ] **P5-3 Degradation**
  ```bash
  docker exec <netns-holder> tc qdisc add dev eth0 root netem delay 200ms loss 5%
  # ... observe mission ... then:
  docker exec <netns-holder> tc qdisc del dev eth0 root
  ```
  Expect: autonomy degrades as designed; local control loops (which never cross the boundary) unaffected.

- [ ] **P5-4 Partition**
  ```bash
  docker network disconnect <stack>_agent_external <comms-container>
  # ... observe ... then reconnect:
  docker network connect <stack>_agent_external <comms-container>
  ```
  Expect: drone-local autonomy continues safely; shared-state consumers handle staleness; clean recovery on reconnect.

- [ ] **P5-5 Netns robustness**
  Restart one workload that shares the comms netns.
  Expect: other workloads' network world survives (netns held by a dedicated `sleep infinity` holder container, not by a restartable service).

## Phase 6 — Multi-drone scale

**Objective:** the entire contract holds at N > 1 (e.g. the 9-drone xfs scenario), and the hardware ceiling is known.
**Exit gate:** all N drones fly simultaneous goals; saturation point recorded.

- [ ] **P6-1 Full stack up**
  Launch the multi-drone scenario, then:
  ```bash
  docker ps --format '{{.Names}}\t{{.Status}}' | grep drone
  ```
  Expect: all SITL instances healthy. A second instance dying with `bind failed on port 5762` means the image lacks per-instance serial port offsets — use the image variant that has them.

- [ ] **P6-2 Per-drone topics**
  ```bash
  r2 topic list | grep -c '^/drone'
  ```
  Expect: every drone has its complete, correctly-prefixed topic set with ≥1 publisher.

- [ ] **P6-3 Aggregate rates**
  Sample `r2 topic hz` across several drones simultaneously.
  Expect: rates hold at N drones. Record the GPU/CPU saturation point (`nvidia-smi`, `htop`) as this hardware's practical ceiling.

- [ ] **P6-4 Swarm goals**
  Send goals to all drones simultaneously.
  Expect: all plan and fly; no cross-drone interference; no TF cross-talk between prefixes.

- [ ] **P6-5 QGC multi-vehicle**
  QGC vehicle list. Expect: all N vehicles, distinct sysids, live telemetry.

## Phase 7 — Repeatability and regression

**Objective:** results are stable enough to compare autonomy builds against each other, and the product is operable from documentation alone.
**Exit gate:** determinism band agreed and met; cold start succeeded by docs alone.

- [ ] **P7-1 Determinism envelope**
  Same scenario + same autonomy build, 3 runs; compare `metrics.json` across runs.
  Expect: key metrics (path length, completion time) within an agreed band — define the band first; sim is not bit-deterministic.

- [ ] **P7-2 Scenario round-trip**
  Edit the scenario in the authoring UI (add an obstacle, move a spawn) → regenerate → relaunch.
  Expect: change visibly reflected in sim; note that regeneration rewrites `generated/<scenario>/.env`, discarding local overrides (e.g. pull policy).

- [ ] **P7-3 Full teardown**
  Stop everything, then:
  ```bash
  docker ps --format '{{.Names}}' | grep -v -E 'dashboard|lichtblick' || echo CLEAN
  du -sh generated/ ${TEVV_RUNS_DIR:-~/tevv-runs}
  ```
  Expect: `CLEAN` (only product services remain); disk usage at expected size.

- [ ] **P7-4 Cold start**
  Reboot the host; reach Phase 3 following only the README + this plan.
  Expect: no tribal knowledge needed. File a doc bug for every step that required help.

## Appendix A — Environment layers

Four env files govern a launch; know which applies to your path:

1. **Top-level `.env`** (with `.env.example` as reference) — scenario shape, images, networking for `launch.sh`-driven scenarios.
2. **`product-images.env`** — pinned review-channel images for the dashboard/authoring flow. Generated from `images/catalog.yaml` (`tools/images.sh sync`); edit the catalog, never this file. Note the top-level `.env` in (1) **wins over it** for any image var it sets — `tools/images.sh report` lists which.
3. **`compose/<scenario>/.env`** — auto-generated by `setup-env.sh`; shadows the top-level file for that scenario.
4. **`generated/<scenario>/.env`** — written by the stack generator for dashboard-launched stacks; regenerated on every generate (local edits are temporary).

## Appendix B — Failure reporting

For each unchecked/failing item record: test ID, scenario name, `generated/<scenario>/` snapshot, container logs of the implicated service, and whether it reproduces on relaunch. Attach `metrics.json`/bags for Phase 4+ failures.
