## Verdict on the review's verdict

Accurate and useful. All five findings verified against primary sources; none were strawmen. Net effect: the variant survives with five amendments and two additional P1 spike items; no architecture change.

## Appendix — raw review output (verbatim)

1. **BLOCKER** | §8 / §9.2 | Attempt isolation fails on reschedule. The variant relies on OSMO's native retries for INFRA_FAILED and preemption, claiming bags safely stream to MinIO. However, OSMO provides no `{{retry_id}}` or `{{attempt}}` token to inject into task environments (verified against OSMO `tokens_table.in.rst`). Consequently, the gang-scheduled `bag-recorder` pod receives static configuration on attempt 2 and uploads bags to the exact same MinIO directory as attempt 1. This overwrites/interleaves data, fatally corrupting the evaluation step. | The conductor (or an init container) must fetch the attempt counter via the OSMO API (or parse it from the OSMO-injected task hostname) and write it to a shared volume. The recorder must dynamically read this file to append the attempt ID to the MinIO upload path (e.g., `<run_id>/<attempt>/bags/`).
2. **BLOCKER** | §7 | OSMO API label cancellation claim is factually wrong. The spec claims `tevv submit` will cancel queued workflows "matching the same {pr, suite} labels via the OSMO API". However, OSMO workflows do not support metadata labels/tags, and the API has no capability to query or bulk-cancel workflows by custom labels. This breaks the CI auto-cancel feature, allowing obsolete commits to starve the cluster. | Query the Postgres run registry (which holds `workflow_ref` and `trigger_ref`) to find the OSMO `workflow_id`s of older runs for the same PR+suite, then issue exact-ID cancel requests to the OSMO API.
3. **MAJOR** | §7 | Intra-run communication dropped by shared-namespace default-deny policy. Shifting to a shared OSMO workflow namespace with per-run default-deny NetworkPolicies that allow "egress only to data-plane endpoints" implicitly blocks all intra-run pod-to-pod traffic (DDS discovery, Zenoh, sim RPCs). In a shared namespace, explicit intra-run exceptions are mandatory. | Update the group template's NetworkPolicy to explicitly allow both Ingress and Egress traffic where the source and destination both match the run label (OSMO supports `{{WF_GROUP_UUID}}` in templates for this exact isolation pattern).
4. **MAJOR** | §8 | Non-lead preemption does not trigger group reschedule. The spec assumes KAI preemption of a LOW run reschedules the gang. However, OSMO groups default to `ignoreNonleadStatus: true`. If KAI preempts a non-lead pod (e.g., a component or SITL pod), OSMO will ignore the failure, leaving the run-conductor (lead) running against a broken stack until a messy watchdog timeout occurs instead of a clean preemption reschedule. | Add `ignoreNonleadStatus: false` to the compiler's OSMO group spec generation to ensure any preempted non-lead pod immediately fails the group and triggers a native reschedule.
5. **MINOR** | §8 | Exit code mismatch for preemption. The lead exit-code contract maps `137 / preemption (FAILED_PREEMPTED)` to the OSMO default reschedule. According to OSMO documentation, tasks preempted by the KAI scheduler receive exit code `3006` with status `FAILED_PREEMPTED`, not `137`. | Update the compiler's `exitActions` generation to explicitly catch exit code `3006` and map it to a reschedule action.

Overall verdict (reviewer): the pivot to OSMO is a scheduling upgrade and fits gang/DNS needs, but the spec "stumbles on the mechanics of migrating from Argo's explicit pipeline state to OSMO's task state"; with the NetworkPolicy patch and registry-backed label queries, "the architecture can safely adopt OSMO for the P1 spike."
